## 2. Safety: Exchange-Native STOP_MARKET Orders

### Problem

`StopMonitor` polls every 1s in-memory. If `friday` crashes, OOMs, or is
killed, all stop protection vanishes. Binance `STOP_MARKET` orders execute
server-side and survive restarts.

### Requirements

- **R1.** `binance.Client.StopMarketOrder(ctx, symbol, side, qty, stopPrice,
  reduceOnly)` — `POST /fapi/v1/order`, `type=STOP_MARKET`, `timeInForce=GTC`.
- **R2.** `binance.Client.CancelOrder(ctx, symbol, orderID) error`.
- **R3.** `binance.Client.OpenOrders(ctx, symbol)` — for startup orphan discovery.
- **R4.** `binance_stop_monitor` tool: after an OPEN fills, place BOTH a native
  STOP_MARKET AND register with the local monitor (dual protection). On CLOSE,
  cancel the native order + clear the local level. When both SL and TP are set,
  two separate native orders are placed.
- **R5.** Startup: query open orders, log any orphaned STOP_MARKET orders
  (cancel if position no longer exists).

### Acceptance Criteria

- [x] `StopMarketOrder` places a `STOP_MARKET` and returns the order ID.
- [x] `CancelOrder` cancels it. `OpenOrders` lists active stop orders.
- [x] After OPEN, `binance_stop_monitor` places native STOP_MARKET AND
  registers with local monitor.
- [x] After CLOSE, native order is cancelled and local level is cleared.
- [x] If native stop fills first, local monitor's subsequent close fails
  harmlessly (position already flat — current behavior handles this).

### Decisions

- **GTC** so the stop survives until explicitly cancelled — the property we want.
- **Two separate orders, not OCO** — simpler, more flexible. Unfilled half
  cleaned up by next CLOSE or overwritten by next OPEN.
- **Local monitor stays** — catches cases where the exchange stop was rejected
  for a transient reason.

## 3. Safety: Fee Budget Guardrail (Anti-Overtrading)

### Problem

PRD-011's reconciliation revealed fees consumed ~36% of total losses — the
system was over-trading. The prompt says "only open when expected move clears
≥3× round-trip fee" but the LLM can overlook it. The circuit breaker tracks
drawdown and consecutive losses, but neither captures death-by-a-thousand-cuts
of fee spend.

### Requirements

- **R6.** `FeeBudget` struct (`internal/risk/fee_budget.go`): rolling window
  (default 30 min), maxFeePct (default 0.5% of balance), ring buffer of
  `{time, fee, balance}` entries. Thread-safe, configurable via
  `FRIDAY_FEE_BUDGET_PCT`.
- **R7.** `FeeBudget.Record(fee, balance)` — called by `log_trade` after
  reconciliation, using the exchange-reconciled `Commission + Funding`.
- **R8.** `FeeBudget.Check(balance) error` — sums fees in window; errors if
  `sumFees / balance > maxFeePct`. Called by `binance_order` before opening
  orders (alongside `CircuitBreaker.Check()`). Reduce-only closes always bypass.
- **R9.** Round prompt includes fee-budget status when nearing the limit.

### Acceptance Criteria

- [x] `FeeBudget` sums fees in window; old entries expire.
- [x] `Check` errors above threshold, nil under.
- [x] `binance_order` blocks openings when budget exceeded; closes pass.
- [x] `log_trade` feeds fee budget with reconciled figures.

### Decisions

- **Window = 30 min, threshold = 0.5%.** At ~0.08% round-trip taker fee, ~6
  round-trips in 30 min hits it. Tuned via env.
- **Session-level, not per-symbol** — overtrading on any symbol bleeds the
  whole wallet.

## 4. Safety: Portfolio-Level Correlation-Aware Sizing

### Problem

7 symbols sized independently to 14% each, but BTC+ETH+SOL are highly
correlated and NVDA+GOOGL+AMZN+META share tech-sector beta. All 7 LONG = 98%
margin in effectively two trades. A broad risk-off move hits everything at once.

### Requirements

- **R10.** `GroupLimits` (`internal/risk/portfolio.go`): `map[string]GroupConfig`
  keyed by group name. `GroupConfig{MaxMarginPct float64, Symbols []string}`.
  Defaults: `crypto` (BTC/ETH/SOL, 30%), `stocks` (NVDA/GOOGL/AMZN/META, 40%).
  Configurable via `FRIDAY_GROUP_LIMITS` env.
- **R11.** `PortfolioGroupValidator` implements `Validator`. Blocks orders that
  push a group over its cap. Wired into `binance_order` alongside
  `MarginCapValidator` (both must pass). Reduce-only always bypasses.
- **R12.** Risk Manager prompt lists each group, its cap, and current usage.

### Acceptance Criteria

- [x] `GroupExposure` correctly identifies which group a symbol belongs to.
- [x] `PortfolioGroupValidator` blocks orders pushing a group over its % cap.
- [x] Symbols not in any group pass through. Reduce-only closes always bypass.
- [x] Risk Manager prompt shows group allocations.

### Decisions

- **Static groups, not dynamic correlation** — crypto moves together, US tech
  stocks move together. Dynamic clustering from price data is a follow-up.
- **Group limits stack with per-position 14% cap** — the tighter limit wins.

## 5. Signal: Online Re-Calibration

### Problem

`backtest.Calibrate` runs once at startup on ~33 days of history. Market
regimes shift; a strategy that crushed a trending month becomes a loser in
chop. With static calibration, the system votes at stale confidence levels for
the entire session.

### Requirements

- **R13.** `Recalibrator` (`internal/strategy/recalibrate.go`): goroutine that
  sleeps `FRIDAY_RECALIBRATE_HOURS` (default 4), fetches fresh 4h×200 candles
  per symbol, calls `backtest.Calibrate`, and updates `registry.SetCalibration`.
- **R14.** A failed re-calibration logs a warning and keeps existing
  confidences. `FRIDAY_RECALIBRATE_HOURS=0` disables.
- **R15.** Uses the same calibration formula as startup: `(winRate − 0.5) × 2`.

### Acceptance Criteria

- [x] `Recalibrator` runs on schedule and updates the live registry.
- [x] A strategy whose backtest win rate dropped from 70% to 45% gets
  confidence updated from 0.4 to 0.0 (abstains).
- [x] Failed run keeps existing confidences.
- [x] `FRIDAY_RECALIBRATE_HOURS=0` disables entirely.

### Decisions

- **4-hour interval** matches the 4h candle close cadence — natural update
  frequency.
- **Full re-fetch of 200 candles per run** — well within rate limits at 7
  symbols.

## 6. Signal: Strategy-Specific Take-Profit

### Problem

The Risk Manager's 7-check TP rules apply uniformly regardless of strategy. But
momentum wants to trail, mean-reversion should exit at MA20, breakout should
target a measured move. The uniform rules cut winners early or hold losers too
long depending on the strategy.

### Requirements

- **R16.** `Signal` gains optional `TakeProfit float64` (0 = n/a).
  - Breakout: entry ± range height (measured move).
  - Mean-reversion: MA20 (the mean to revert to).
  - Momentum, EMACross: 0 (rely on trailing stop — no fixed TP).
- **R17.** `names()` and `mtfPart()` in aggregator render `tp=…` when non-zero.
- **R18.** `Calibrate` runs a coarse TP sweep per strategy ([0.5%, 1.0%, 1.5%,
  2.0%, 3.0%]) and selects the TP with best total return.
- **R19.** Risk Manager prompt: "If strategy signals include `tp=…`, use it as
  the tier-1 TP target INSTEAD of the fixed +10% rule. Trailing stop and
  tier-2 (+20%) still apply as safety nets."

### Acceptance Criteria

- [x] Breakout `Signal` carries `TakeProfit = range height`.
- [x] Mean-reversion `Signal` carries `TakeProfit = MA20`.
- [x] `names()` renders `tp=…` when non-zero.
- [x] `Calibrate` TP sweep selects best TP.
- [x] Risk Manager prompt references strategy TP levels.

### Decisions

- **Momentum and EMA cross return TP=0 intentionally** — these strategies work
  best with trailing exits. The Risk Manager's trailing stop already provides
  this.
- **TP is informational for the Risk Manager, not enforced in code** —
  consistent with the current design where the Risk Manager owns exit decisions.

## 7. Signal: Bollinger Band Strategy

### Problem

The existing mean-reversion strategy uses a fixed 2% deviation from MA20, which
doesn't adapt to volatility changes. Bollinger Bands (MA20 ± 2×stddev)
automatically widen in high vol and narrow in low vol. Additionally, a band-walk
(price walking the upper band with expanding bandwidth) is a strong trend signal
not captured by existing strategies.

### Requirements

- **R20.** `binance.BollingerBands(closes, period=20, multiplier=2.0)` returns
  `(mid, upper, lower, bandwidth, ok)`.
- **R21.** `Bollinger` strategy (`internal/strategy/bollinger.go`):
  - **Mean-reversion LONG:** `close <= lower` and `RSI(14) < 35` → fade up.
    Invalidation = `lower`.
  - **Mean-reversion SHORT:** `close >= upper` and `RSI(14) > 65` → fade down.
    Invalidation = `upper`.
  - **Band-walk LONG:** close > mid, near upper band, bandwidth > 5% and
    expanding, RSI [50,70] → trend continuation. Invalidation = `mid`.
  - **Band-walk SHORT:** mirror.
  - Confidence: 0.55 base for mean-reversion, 0.50 for band-walk + ADX boost.
  - If both fire, pick the higher-confidence one.
- **R22.** Registered in `DefaultRegistry()`.

### Acceptance Criteria

- [x] `BollingerBands` matches hand-calculated values.
- [x] Mean-reversion LONG fires at band touch with oversold RSI.
- [x] Band-walk LONG fires on expanding band walk.
- [x] Both stay NEUTRAL on contracting bandwidth.
- [x] `DefaultRegistry()` returns 5 strategies.

### Decisions

- **RSI filter on mean-reversion** prevents fading a band touch that's actually
  a breakout.
- **Band-walk needs bandwidth expansion** to distinguish a true trend from a
  slow grind.
