---

## 1. Summary

Max leverage is **per-symbol** on Binance (BTC 125×, ETH 100×, SOL 50×, the
TradFi stock perps just **10×**), but the Risk Manager prompt hardcoded
"1x–100x" and `binance_leverage` passed the LLM's number straight through —
so a 100× request on a stock perp was rejected with `-4028`. PRD-012 captures
each symbol's max at startup, **injects it into the Risk Manager prompt** and
**clamps it in code**, so over-cap requests are corrected instead of failing.

---

## 2. Problem

Two gaps surfaced live:
- `binance_leverage: setLeverage: ... -4028 "Leverage 100 is not valid"` — the
  Executor set 100× on a symbol capped at 10×.
- The margin guardrail then blocked a hugely over-sized order — same root
  weakness: the LLM-driven Risk Manager wasn't given (and couldn't infer) the
  per-symbol leverage ceilings, and nothing in code enforced them.

## 3. Goals / Non-Goals

**Goals**
- Resolve each symbol's max leverage at startup (alongside step size).
- Tell the Risk Manager each symbol's cap (prompt injection).
- Clamp an over-cap leverage request in `binance_leverage` (never `-4028`).

**Non-Goals**
- The 15% margin guardrail stays **reject-and-report** — it does NOT auto-resize
  oversized orders (chosen for transparency); the prompt now explains the
  leverage↔margin interaction so the Risk Manager sizes correctly.
- Not per-notional bracket modelling — we use the single highest `initialLeverage`.

## 4. Requirements

- **R1.** `binance.MaxLeverages(ctx) map[string]int` — `/fapi/v1/leverageBracket`
  (signed); a symbol's max is the highest `initialLeverage` across its brackets.
- **R2.** `MarketSymbol.MaxLeverage`; `bootstrap.resolveSymbols` fetches the caps
  (when credentials are present), attaches them to each symbol, and installs the
  map via `tool.SetMaxLeverages`.
- **R3.** Risk Manager prompt: the steps hint renders each symbol as
  `NAME step (≤Nx)`, and the caps line says "leverage 1x up to EACH SYMBOL'S
  MAX" with a note that low-leverage symbols cost more margin for the same
  notional (sanity-check `notional ÷ leverage ≤ 0.14 × balance`).
- **R4.** `binance_leverage` clamps a requested leverage above the symbol's known
  max down to that max, logs it, and proceeds (so the order never fails -4028).
  Unknown symbol → no clamp (best-effort).

## 5. Acceptance Criteria

- [x] `MaxLeverages` picks the highest bracket per symbol; empty-bracket symbols

- [x] `binance_leverage` clamps an over-cap request (100× on a 10× symbol → 10×).

- [x] The Risk Manager prompt shows each symbol's `(≤Nx)` cap. —
      `internal/orchestrator/prompts_test.go`.
- [x] `go build ./...` and `go test ./...` pass.

### Decisions & notes

- Verified testnet caps: BTC 125, ETH 100, SOL 50, NVDA/GOOGL/AMZN/META 10.
- Clamp is **belt-and-suspenders** with the prompt: even if the LLM over-asks,
  the code corrects it; the prompt aims to have it ask correctly in the first
  place.
- `leverageBracket` is signed, so the caps preflight is skipped without
  credentials — the clamp then no-ops and the exchange remains the backstop.

## 6. Out of Scope / Follow-ups

- Per-notional-bracket leverage (large positions drop to a lower max tier).
- Authoritative code-side **position sizing** (use `risk.SuggestedSize` as the
  source of truth) so the margin guardrail rarely needs to fire — a larger
  change than this clamp; the guardrail stays reject-and-report until then.
