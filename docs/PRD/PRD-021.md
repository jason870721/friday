## 1. Summary

Three tools to make Friday operable without constant attention: a post-mortem
analysis CLI that reads the round and trade logs, external notifications for
critical events (breaker trips, large PnL), and a paper trading mode for safe
strategy validation.

---

## 2. Post-Mortem Analysis Tool

### Problem

Friday records two structured logs — `rounds.jsonl` (every round's full
pipeline) and `trades.jsonl` (every closed trade) — but has no tool to read
them. After a session, the operator can't answer basic questions like "did
momentum make money today?" or "was the Analyst's bias accurate?"

### Requirements

- **R1.** `cmd/analyze/main.go` — reads `~/.friday/memory/rounds.jsonl` and
  `trades.jsonl` (paths overridable via `-rounds` / `-trades` flags).
- **R2.** Flag `-json` outputs structured JSON; default is a terminal-formatted
  text report.
- **R3.** Report sections:
  1. **Session overview:** rounds run, trades taken, time range, total PnL,
     total fees, max drawdown.
  2. **Per-strategy:** trades, win rate, total PnL, avg PnL/trade, profit
     factor (gross wins / abs(gross losses)).
  3. **Per-symbol:** same stats by symbol.
  4. **Per-regime:** trades in TRENDING vs RANGING vs TRANSITIONAL, win rate per
     regime overall and per strategy (requires Regime to be recorded in the
     round log — see R8).
  5. **Analyst accuracy:** for rounds where a directional bias was given and a
     trade was opened, was the bias correct? (Bias matches outcome direction.)
  6. **Breaker timeline:** rounds where breaker was PAUSED/HALTED, with reason
     and duration.
- **R4.** Graceful degradation: empty/missing files → zeros, not a crash.

### Acceptance Criteria

- [x] `go run ./cmd/analyze` prints all 6 sections.
- [x] `-json` outputs valid JSON.
- [x] Empty trades file → zeros, no crash.
- [x] Missing rounds file → trade-only report, no crash.
- [x] `go build ./cmd/analyze` compiles.

### Decisions

- **Analyst accuracy is directional only** — "Analyst said BULLISH, trade was
  LONG, WIN → correct." Not measuring conviction calibration quality
  (Brier score is a follow-up).
- **Profit factor >1.0** means the strategy earns more on winners than it loses
  on losers. Single most important per-strategy metric.

## 3. External Notifications (Discord / Telegram)

### Problem

Friday runs indefinitely in a terminal. The operator must actively watch the
TUI to know if the circuit breaker tripped, a position hit stop-loss, or the
session is bleeding. A HALTED breaker means the system sits idle until manually
reset — hours of dead time if unnoticed.

### Requirements

- **R5.** `Notifier` interface (`internal/notify/notifier.go`):
  `Notify(title, body string) error`.
- **R6.** `DiscordNotifier` — `POST` to `FRIDAY_DISCORD_WEBHOOK_URL`. Body
  truncated to 2000 chars. `TelegramNotifier` — `POST` to
  `https://api.telegram.org/bot<TOKEN>/sendMessage` with
  `FRIDAY_TELEGRAM_BOT_TOKEN` + `FRIDAY_TELEGRAM_CHAT_ID`.
- **R7.** `MultiNotifier` fans out to multiple. `NewFromEnv()` returns nil if
  none configured.
- **R8.** Event wiring:
  - Circuit breaker PAUSED/HALTED → notify with reason and current PnL (once
    per state transition, not every round).
  - Trade closes with net PnL exceeding ±X% of balance (configurable,
    `FRIDAY_NOTIFY_PNL_PCT`, default ±5%) → notify with symbol, strategy, net PnL.
  - Session start: "Friday started — trading N symbols on <endpoint>".
  - Session stop (clean shutdown): session summary.

### Acceptance Criteria

- [x] `DiscordNotifier.Notify` sends a message to the webhook.
- [x] `TelegramNotifier.Notify` sends a message to the chat.
- [x] Breaker PAUSE → HALT sends ONE notification (not per round).
- [x] No webhook configured → nil Notifier → no-op, no errors.
- [x] `go build ./...` and `go test ./...` pass.

### Decisions

- **Event dedup** — a `lastNotifiedState` tracker in the orchestrator ensures
  each state transition fires once.
- **Plain text only**, no markdown. Discord auto-links URLs.
- **Discord rate limit 30/min, Telegram 20/min** — significant-events-only
  means this will never be hit.

## 4. Paper Trading Mode

### Problem

Testing strategy changes requires a live testnet session with real order
placement. Testnet USDT can be lost, rate limits consumed, and comparing two
strategies requires two separate sessions. A paper trading mode lets the
operator validate changes safely and iterate faster.

### Requirements

- **R9.** `FRIDAY_PAPER=true` env var. Printed prominently at startup.
- **R10.** `PaperPortfolio` (`internal/risk/paper.go`): thread-safe in-memory
  tracker. `Open/Close/Positions/Balance` at mark price. Virtual balance
  initialised from `FRIDAY_PAPER_BALANCE` (default 1000 USDT).
- **R11.** Trading tools (`binance_order`, `binance_leverage`,
  `binance_close_all`, `binance_stop_monitor`) become no-ops that log "PAPER:
  would have…" and update `PaperPortfolio`. `binance_position` and
  `binance_balance` return virtual state.
- **R12.** Market-data tools (`binance_price`, `binance_klines`,
  `binance_mtf_klines`) work normally against the real exchange.
- **R13.** Round log and trade log written with `paper: true` tag.

### Acceptance Criteria

- [x] `FRIDAY_PAPER=true go run ./cmd/friday` prints "PAPER TRADING MODE".
- [x] `binance_order` logs "PAPER: would have…" and updates virtual positions.
- [x] `binance_position` shows virtual positions, not real exchange positions.
- [x] Real exchange account endpoints are never called.
- [x] Market data still comes from the real exchange.
- [x] Round log and trade log tagged with `paper: true`.
- [x] `go build ./...` and `go test ./...` pass.

### Decisions

- **Fill price = mark price, no slippage** — makes paper results optimistic.
  Configurable slippage model is a follow-up.
- **Virtual balance is isolated** — real Binance client only fetches market
  data; account endpoints are never called.
- **Paper StopMonitor still works** — uses `PaperPortfolio.CloseReduceOnly`
  instead of the exchange.
- **Why not use Binance testnet as "paper"?** Testnet still consumes rate
  limits, requires faucet refills, and can't run side-by-side with a live
  session for strategy comparison.

## 5. Out of Scope / Follow-ups

- Real-time dashboard (web UI or TUI tab).
- Conviction calibration scoring (Brier score).
- Export to CSV/Parquet.
- Session comparison mode (diff two sessions).
- Interactive notification commands (reply to reset breaker).
- Slack/email/PagerDuty notification providers.
- Slippage modeling in paper mode.
- Side-by-side strategy comparison (two paper portfolios, same data).
- Historical replay mode (feed recorded market data instead of live).
- Paper portfolio persistence across restarts.
