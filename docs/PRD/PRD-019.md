# PRD-019 — Per-Notional Leverage Tier Clamp (avoids -2027)

| Field        | Value                                                       |
|--------------|-------------------------------------------------------------|
| Status       | Implemented & verified                                      |
| Tranche      | Operational hardening                                       |
| Owner        | Friday team                                                 |
| Source       | Operational — testnet `-2027 "Exceeded the maximum allowable position at current leverage."` on AMZNUSDT (blocked 3 rounds by the $5,000 notional cap) |
| Depends on   | [PRD-012](./PRD-012.md)                                     |
| Blocks       | —                                                           |

---

## 1. Summary

Binance leverage brackets are tiered **by notional**: the highest leverage is
only available for the **smallest** notional tier (e.g. AMZNUSDT allows 10× only
up to a **$5,000** position; bigger positions must drop to 5×, then 2×). PRD-012
captured a symbol's single highest `initialLeverage` and injected it as `≤Nx` —
which, combined with margin-based sizing, *guaranteed* the conflict: at max
leverage the Risk Manager sized a notional far above the tier's cap, and the
Executor's order was rejected with `-2027`. PRD-019 captures the **full
tier table**, **auto-lowers leverage in `binance_order`** so the position fits
the tier its notional falls into, and **injects the max-leverage notional
ceiling into the Risk Manager prompt** so it sizes correctly up front. This is
the per-notional-bracket follow-up explicitly deferred in PRD-012's Out-of-Scope.

---

## 2. Problem

`-2027` is a *different* limit from PRD-012's `-4028`:

- `-4028` — leverage above the symbol's absolute max. **Fixed by PRD-012.**
- `-2027` — at the *current* leverage, the position's notional exceeds the tier
  that leverage permits. **Not addressed by PRD-012** — the leverage clamp can't
  see the order's notional, and the reported "max leverage" is only usable for
  the smallest tier.

Concretely on AMZNUSDT (max 10× ⇒ tier cap $5,000): with a $15k balance the Risk
Manager sized to ~14% margin × 10× ≈ $21k notional — over 4× the $5k tier cap —
so every OPEN was rejected `-2027`, three rounds running.

## 3. Goals / Non-Goals

**Goals**
- Capture each symbol's full notional→leverage tier table at startup.
- Auto-lower leverage in `binance_order` to the tier the order's notional falls
  into, so an OPEN never fails `-2027`.
- Show the Risk Manager each symbol's max-leverage notional ceiling so it sizes
  within the tier (or deliberately picks a lower leverage) from the start.

**Non-Goals**
- The 15% margin guardrail stays **reject-and-report**. After leverage is
  auto-lowered, margin is re-validated at the *lower* leverage; a position too
  big to fit both the tier and the 15% cap is cleanly rejected (not auto-resized).
- No exchange-native bracket selection / cross-margin tiering — we only clamp the
  isolated-margin initial leverage we already set.

## 4. Requirements

- **R1.** `binance.LeverageBrackets(ctx) map[string][]LeverageBracket` —
  `/fapi/v1/leverageBracket` (signed), parsing `notionalCap` + `initialLeverage`,
  sorted ascending by cap. `MaxLeverages` is reimplemented on top of it (no
  second API call). `binance.MaxLeverageForNotional(brackets, notional)` returns
  the highest leverage permitted for a notional (smallest tier whose cap covers
  it; lowest-leverage tier as the floor when the notional exceeds every cap).
- **R2.** `bootstrap.resolveSymbols` fetches the tier table once (when
  credentials are present), derives the max-leverage map + each symbol's
  max-leverage notional ceiling (`MarketSymbol.MaxNotional`), installs the table
  via `tool.SetLeverageBrackets`, and the max map via `tool.SetMaxLeverages`.
- **R3.** `binance_order`, on a non-reduce-only order with a known table: compute
  notional = quantity × mark; if the configured leverage exceeds
  `maxLeverageForNotional`, re-set leverage down to that value before the order,
  note it in the result, and re-validate the margin guardrail at the lower
  leverage. Unknown table → no clamp (fail open; the exchange stays the backstop).
- **R4.** Risk Manager prompt: the steps hint renders `≤$Xk @max-lev`, and a
  "Notional tier cap" section explains that max leverage is only usable for a
  small position and bigger notionals need a lower leverage (more margin).

### Decisions & notes

- The clamp lives in `binance_order` (not `binance_leverage`) because only the
  order knows the notional — it's the last line of defense and runs regardless of
  what leverage `binance_leverage` set.
- **Belt-and-suspenders** with the prompt, exactly like PRD-012: the prompt aims
  to have the Risk Manager size within the tier; the code corrects it if not.
- Lowering leverage raises the margin requirement, so the guardrail re-check at
  the lower leverage is intentional — an order that can't satisfy both limits is
  rejected with the existing clear margin message, not silently `-2027`.

## 6. Out of Scope / Follow-ups

- Authoritative code-side position sizing (carried over from PRD-012) so neither
  the tier clamp nor the margin guardrail normally needs to fire.
- Surfacing the *next* tier's leverage to the Risk Manager so it can opt into a
  bigger notional at a lower leverage deliberately, rather than relying on the
  auto-lower + possible guardrail rejection.
