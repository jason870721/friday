## 1. Summary

The per-trade `MarginCapValidator` (PRD-002) stops one oversized order, but
nothing stops the system from bleeding out across *many* correctly-sized
trades. This PRD adds **session-level circuit breakers** in
`internal/risk` that block new entries when daily loss, consecutive losses,
or total drawdown breach thresholds — and force a flatten on a hard
drawdown.

---

## 2. Problem

- Friday could lose 5% over 20 small trades and keep going — no daily loss
  limit.
- A bad-decision feedback loop has no automatic pause.
- Only the user (Ctrl+C) can stop trading; there is no code-level kill
  switch for catastrophic sessions.

---

## 3. Goals / Non-Goals

**Goals**
- Track session realized PnL, consecutive losses, and drawdown.
- Block new entries (closes still allowed) on breach; auto-flatten on a
  hard drawdown; cooldown then resume at reduced size.

**Non-Goals**
- No cross-restart persistence in v1 (in-memory; documented limitation).
- No change to per-trade sizing logic (that's PRD-007).

---

## 4. Requirements

### 4.1 The breaker (`internal/risk/circuit_breaker.go`)

- **R1.** `CircuitBreaker` with states `Normal / Warning / Paused / Halted`
  and methods `RecordTrade(pnl, balance)`, `Check(balance) error`,
  `UpdateDrawdown(unrealizedPnL)`, `Status() string`. Pure/deterministic,
  unit-testable.
- **R2.** Thresholds configurable via env with sensible defaults:
  `FRIDAY_DAILY_LOSS_PCT` (0.10), `FRIDAY_MAX_CONSEC_LOSSES` (5),
  `FRIDAY_DRAWDOWN_HALT_PCT` (0.20), `FRIDAY_COOLDOWN_CYCLES` (20).
- **R3.** Breach behaviour: daily realized loss ≤ −10% → `Paused`
  (cooldown, then resume at reduced size); 5 consecutive losses → `Paused`
  (reset on first win); total drawdown ≤ −20% → `Halted` (flatten + only
  WAIT until manual reset); cooldown expiry → `Normal`.

### 4.2 Wiring (current architecture)

- **R4.** A process-wide `globalBreaker` checked in
  [`internal/tool/binance_order.go`](../../internal/tool/binance_order.go)
  **before** the existing `MarginCapValidator`; a blocked open returns an
  actionable error. Reduce-only closes always pass.
- **R5.** Construct the breaker in `bootstrap.New` (reads env) and pass it
  into `orchestrator.New`; feed it from the round loop —
  `RecordTrade` on each closed trade (the Executor already closes +
  `log_trade`s in PRD-004; hook the same close events) and
  `UpdateDrawdown` from positions each round.
- **R6.** Surface `breaker.Status()` into the **Risk Manager** (and
  Analyst) round prompts via the orchestrator's `carry`/prompt builders —
  *not* a wakeup-prompt string (that mechanism no longer exists). When
  `Paused`/`Halted`, the Risk Manager may only emit `CLOSE`/`WAIT`; update
  `riskSystemPrompt` in [`internal/orchestrator/prompts.go`](../../internal/orchestrator/prompts.go) accordingly.

## 5. Acceptance Criteria

- [x] Each breach condition (daily loss, consecutive losses, drawdown halt)
      transitions state correctly; cooldown expires back to Normal —
      `internal/risk/circuit_breaker_test.go` (7 cases).
- [x] A new opening order is blocked by Go code when the breaker is
      Paused/Halted, before reaching Binance; reduce-only closes pass. —
      `Check()` gate in `binance_order.go`;
      `internal/tool/circuit_breaker_tool_test.go` proves block + bypass.
- [x] Breaker status appears in the Risk Manager's prompt, and a
      Paused breaker yields only CLOSE/WAIT decisions. — `o.breakerLine()`
      injects `Status()` into the Risk/Analyst prompts;
      `riskSystemPrompt` enforces CLOSE/WAIT-only when not NORMAL. (Live
      LLM compliance to confirm in a runtime session.)
- [x] `go build ./...` and `go test ./...` pass.

---

## 6. Out of Scope / Follow-ups

- SQLite (or file) persistence of breaker state across restarts.
- A TUI command / env flag to manually reset a `Halted` breaker.
