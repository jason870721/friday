## 1. Summary

Expand Friday's decision dimensions beyond price action, and add a
deterministic safety layer that the LLM cannot talk its way past. The model
gains sentiment inputs; the system gains a **hard-coded pre-trade
guardrail** that physically blocks unsafe orders.

---

## 2. Problem

- Decisions rely only on the symbol's own price/indicators — no macro
  sentiment context, so the agent can lean long into a fearful market.
- The seven risk checks today live in the *prompt*. A prompt is advisory:
  a confused or jailbroken model can still emit an oversized order. There
  is no code-level circuit breaker between "decide" and "execute".

---

## 3. Goals / Non-Goals

**Goals**
- Give the agent callable tools for market-wide sentiment.
- Insert deterministic Go logic that blocks orders exceeding a safe size
  *before* they reach Binance.

**Non-Goals**
- No multi-agent split yet ([PRD-003](./PRD-003.md)).
- No persistence / memory ([PRD-004](./PRD-004.md)).

---

## 4. Requirements

### 4.1 Sentiment tools

- **R1.** Add a `fear_greed_index` tool (Crypto Fear & Greed Index) that
  returns the current value + classification, following the existing custom
  tool pattern (`internal/tool/echo.go` as reference, `pkg/tools.Tool`).
- **R2.** Optionally add a financial-news tool returning recent headlines
  for the traded symbols. **DEFERRED** — Fear & Greed (R1) covers the
  sentiment dimension for this phase; a news tool can be added later
  following the same pattern without touching the guardrail.
- **R3.** Register new tools at agent construction via
  `agent.WithCustomTool` in
  [`internal/bootstrap/bootstrap.go`](../../internal/bootstrap/bootstrap.go).

### 4.2 Pre-trade guardrail (hard-coded)

- **R4.** Model the guardrail as a Go **validator struct / middleware
  interface** (e.g. `type OrderValidator interface { Validate(order) error }`)
  on the execution path — invoked after the agent produces a trade action
  but **before** the signed Binance call in
  [`internal/tool/binance_order.go`](../../internal/tool/binance_order.go)
  (or a shared chokepoint). A middleware shape keeps the check composable
  and unit-testable in isolation.
- **R5.** The validator checks proposed notional/margin against a safe
  threshold derived from the live wallet balance. `plan.md` cites *5% of
  total balance* as the example ceiling; reconcile with the existing
  dynamic caps (15% per-position / 60% total) and make the threshold a
  named, runtime-computed parameter — never a hard-coded dollar figure,
  consistent with the README's dynamic-cap design.
- **R6.** On breach: **block** the order, return a structured Go error to
  the agent explaining the violation, and prompt it to recalculate. No
  order is sent on breach.

## 5. Acceptance Criteria

- [x] `fear_greed_index` returns a live value and appears in the agent's
      tool catalog. — `internal/tool/fear_greed.go`, registered in
      `bootstrap.go`; tested end-to-end via httptest stub. (Live value to
      confirm in a runtime session.)
- [x] An order request exceeding the per-position cap is rejected by Go
      code (covered by a unit test with a mocked balance), and never hits
      the Binance client. — `risk.MarginCapValidator` runs in
      `binance_order.go` before `cli.MarketOrder`;
      `internal/risk/guardrail_test.go` covers block/allow/exempt cases.
- [ ] The rejection message is actionable and the agent retries with a
      smaller size in a live testnet session. — runtime verification.
- [x] `go build ./...` and `go test ./...` pass.
