# PRD-014 — Strategy Performance Tracking

| Field        | Value                                                       |

| Status       | Implemented & verified                                      |
| Tranche      | P2 — strategy-engine hardening                              |
| Owner        | Friday team                                                 |

---

## 1. Summary

Attribute every closed trade to the strategy that triggered it, and use that
attribution to power outcome-filtered recall queries. `TradeRecord` gains a
`strategy` field; `recall_trades` returns win/loss breakdowns per strategy;
`log_trade` accepts the triggering strategy name from the Executor. This closes
the feedback loop: the system can now answer "which strategies are winning, and
under what conditions?"

---

## 2. Problem

Currently `TradeRecord` stores market features (RSI, price-vs-MA, momentum,
funding, sentiment) and an `entry_reason` string, but **no field identifies
which strategy triggered the trade**. `recall_trades` returns similar past trades
sorted by feature-vector similarity, agnostic to whether those trades were
momentum entries, breakout entries, or something the LLM invented. The Analyst
sees "3 similar trades: 2 WIN, 1 LOSS" but has no way to ask "how did momentum
do in conditions like these?"

This makes it impossible to:
- Track rolling win rate per strategy (→ can't auto-disable a losing strategy).
- Calibrate strategy confidences from actual outcomes (→ PRD-015 is blocked).
- Let the Analyst weight signals by their historical reliability.

---

## 3. Goals / Non-Goals

**Goals**
- `TradeRecord` carries a `strategy` field populated at log time.
- `recall_trades` output includes per-strategy win/loss counts for the returned
  similar trades.
- `Store` gains an outcome-summary query and a strategy-filtered similarity query.
- Executor prompt instructs the model to pass the strategy name to `log_trade`.

**Non-Goals**
- No change to how trades are opened or closed.
- No real-time strategy disable/enable logic (that's PRD-016).
- No change to the feature-vector format or cosine similarity algorithm.

## 4. Requirements

### 4.1 TradeRecord schema — `internal/memory/store.go`

- **R1.** `TradeRecord` gains `Strategy string` (`json:"strategy,omitempty"`).
  Empty for pre-PRD-014 records (backward-compatible).
- **R2.** `Store.OutcomeSummary(symbol string, f Features, k int) OutcomeStats`
  — returns `{Wins, Losses, Flats int; AvgWin, AvgLoss float64}` for the top-k
  similar trades. Used by `recall_trades` to annotate results.
- **R3.** `Store.SimilarByStrategy(symbol, strategy string, f Features, k int)
  []Scored` — same as `Similar()` but only considers records whose `Strategy`
  matches. Used when the Analyst wants to ask "how did momentum specifically do?"

### 4.2 log_trade — `internal/tool/log_trade.go`

- **R4.** `logTradeInput` and its JSON schema gain an optional `strategy` field
  (string, not required — backward-compatible with any existing prompt that omits it).
- **R5.** `Execute()` writes `in.Strategy` into `rec.Strategy`.

### 4.3 recall_trades — `internal/tool/recall_trades.go`

- **R6.** Output format updated: after listing similar trades, append a summary
  line: `Outcome: N wins, M losses (avg win +$X, avg loss -$Y)`. When multiple
  strategies appear in the results, break it down per strategy.
- **R7.** Schema gains an optional `strategy` filter — when set, only that
  strategy's trades are recalled.

### 4.4 Executor prompt — `internal/orchestrator/prompts.go`

- **R8.** The `log_trade` call instruction in the Executor prompt (§ "Closing a
  trade → log it") updated to include the strategy name: "Pass the strategy that
  triggered this trade (from the Risk Manager's decision reason) as the
  `strategy` parameter."

- [x] Executor prompt references the "strategy" parameter (§ "Closing a trade →

- [x] `go build ./...`, `go vet ./...`, and `go test ./...` pass.

### Decisions & notes

- **Strategy names are free-form strings**, not an enum. The Risk Manager's
  decision `reason` field already names setups like "momentum continuation on
  BTCUSDT" — the Executor extracts the strategy name from that context. A future
  iteration could add a structured `strategy` field to `RiskDecision` to remove
  the parsing ambiguity.
- **`OutcomeSummary` uses `NetPnL` when `PnLSource == "exchange"`, else
  `PnL`** — consistent with `DeriveOutcome()` (PRD-011). This means WIN/LOSS
  breakdowns reflect true wallet impact.
- The `strategy` field on `recall_trades` input is **optional** — omitting it
  returns all strategies, which preserves the current "show me what happened in
  similar conditions" workflow.

---

## 6. Out of Scope / Follow-ups

- Real-time strategy disable when rolling win rate drops below a threshold
  (PRD-016).
- Structured `strategy` field on `RiskDecision` (avoid LLM string-parsing at the
  Executor).
- A dashboard / metrics endpoint exposing per-strategy Sharpe, profit factor,
  etc.
